## 0. 30초 요약

**별건으로 등록해서 고치시는 쪽을 권합니다.** 저희(CRM) 영향은 0이라 급할 이유는 없는데,
그쪽 코드를 보니 미러 옵션·색상이 **죽은 데이터가 아니라 견적 워크벤치가 실제로 소비 중**입니다.
방치하면 저희 마스터에 신차 트림이 등록될 때마다 그 차의 옵션·색상이 그쪽 화면에서 **영구히 비는**,
시간이 갈수록 커지기만 하는 단방향 갭이 됩니다. #115에서 고치신 "조용한 드리프트"와 같은 성격입니다.

dry-run 수리(#115)와 무변경 UPSERT 스킵은 확인했습니다 — 보고드린 것 전부 반영됐고,
"10,495 = 무변경 UPSERT" 실측 확정도 잘 받았습니다. 감사합니다.

## 1. 근거 — 소비 체인이 살아 있습니다 (그쪽 코드)

```
src/domain/catalog/master-options.ts          ← 미러 options/colors read-only 쿼리 (mc_code → trim id resolve)
  → src/routes/catalog.ts                     ← /api/catalog/master/trims/:mcCode/options · /colors
    → client/src/lib/api.ts                   ← fetchTrimOptions / fetchTrimColors
      → client/src/pages/QuoteRevolutionV2.tsx ← useTrimOptions(mcCode) · useTrimColors(mcCode)
```

즉 상담 화면이 mc_code로 트림을 고르면 옵션·색상이 이 미러에서 나갑니다. FK 스킵은 에러 없이
빈 목록으로 떨어지는 fail-open이라, **새 차종일수록 "옵션 없음·색상 없음"으로 조용히 보이는**
유형입니다 — 화면만 봐서는 데이터 결손인지 진짜 무옵션인지 구분이 안 됩니다.

## 2. 갭의 성격 — 지금 56건은 시작점입니다

- 말씀하신 대로 그쪽 `trims.id`는 자체 시퀀스라 Mr.Cha trim id와 **영구히** 다릅니다 →
  sync가 새로 만든 트림의 위성 행은 다음 sync에서도 계속 스킵됩니다. 자연 치유가 없습니다.
- 갭은 **신규 트림에서만** 생기고 누적만 됩니다. 저희 마스터에 차량이 등록되는 속도만큼 자랍니다.
  지금 걸린 colors 56건이 이미 그 증거입니다.
- 참고로 수리 방향은 그쪽 판단이지만, trims를 mc_code 안정 키로 upsert하시는 설계 그대로라면
  위성 테이블도 **Mr.Cha trim id → mc_code → 그쪽 trims.id** 한 번 매핑을 거치면 될 것으로
  보입니다(이번에 dry-run·apply가 같은 쿼리를 쓰게 하신 것과 같은 결로 넣기 좋아 보입니다).

## 3. 저희 쪽 영향 — 0입니다

- CRM은 파트너 API의 **계산 응답만** 소비하고 옵션·색상은 계산에 들어가지 않습니다.
- 링크 매칭·검출축도 전부 mc_code 트림 레벨이라 위성 테이블 결손과 무관합니다.
- 따라서 저희 코드 조치는 없고, 이 문서는 요청하신 **판단 회신**입니다. 우선순위는
  그쪽 워크벤치에서 신차 견적을 얼마나 자주 만드는지에 달려 있으니 최종 판단은 그쪽에 맡깁니다.
