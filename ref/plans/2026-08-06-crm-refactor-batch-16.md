## P1 — B 보존 고객 재연결 시 파기 (CONFIRMED · 중) 🔴 유일한 실동작 결함

`listRetentionDueCustomers`(`src/db/queries/account-deletion.ts`)가 `retention_until <= now()`만 보고
**앱 연결 여부를 보지 않는다.** `applyAppUserLink`(`app-user-link.ts`)도 연결 시 retention 2컬럼을 클리어하지 않는다.
레포 전체에서 그 컬럼 **write는 B 실행 1곳뿐이고 클리어는 0곳**(전수 grep).

**적대 검증이 반박에 실패한 결정적 이유**: 앱 팀 회신 §8이 재연결을 **정상 경로로 명시**한다 —
> B 보존 고객은 phone이 materialize돼 **매칭 후보에 뜰 수 있으나 후보 표시까지만** — 직원이 본인·거래 확인 후 수동 연결

즉 "운영상 도달 불가"라는 반박이 성립하지 않는다. 방어는 8개 각도(다른 클리어 경로·DB 트리거/CHECK·
크론 필터·`purgeCustomerCore` 가드·연결 경로 유일성·매칭 후보 조건·기존 테스트·UI 경고) 전부에서 부재.

**원인의 정확한 형태** — 주석이 시점 사실을 영구 불변식으로 썼다:
```
// 이 컬럼은 B 실행만 기록하므로 값이 있다 = 보존 고객이다(앱 연결은 이미 해제 상태).
```
괄호 안이 **B 실행 시점에만 참**이다.

**현재 노출 0**(실측: `retention_until IS NOT NULL` 0건 · B 분류 미사용). 이건 "지금 안전"이지 반박이 아니다.
발동 4단 = B 확정 → 같은 번호 앱 재가입(**같은 번호 다중 계정 3그룹 실재**) → 상담사 수동 연결 → 기한 도래.
피해 = 재연결 후 새로 쌓인 견적·서류까지 `purgeCustomerCore` 전량 파기 + **앱 카드 회수**. 유일한 신호는 **파기 후** 디스코드 알림.

**수정 2택 — 성격이 다르다**
- ⓐ `listRetentionDueCustomers`에 `AND app_user_id IS NULL` → **순수 안전장치, 정책 판단 0** ← 이번 배치에서 이것만
- ⓑ `applyAppUserLink`에서 retention 2컬럼 클리어 → **"연결로 보존 의무가 소멸하는가"는 정책** — 유슨생/이사님 영역

## S1 — 정산 금액 null 덮어쓰기 (ADJUSTED · 중 · 잠복)

`DeliveryInfoPopover`가 정산 3키(`settledAt`·`feeAmount`·`costs`)를 **무조건** 저장 payload에 싣고,
저장 버튼은 `saving`(출고 PUT 진행 중)만 보고 disable된다 → 정산 GET이 실패했거나 아직 안 끝난 상태에서
저장하면 `{settledAt:null, feeAmount:null, costs:[]}`가 나가 **기존 금액이 지워진다**(이력 테이블·트리거 0, 복구 불가).

**적대 검증의 정정 2가지**
- ❌ 원 주장의 원인 진단("서버의 부분 갱신 보호가 무력화")이 **틀렸다.** 서버의 부분 SET은 *팝오버(금액)와 담당자 요청(status)이
  서로를 덮지 않게* 하는 축 분리다. 금액의 유일한 편집자가 팝오버이므로 "항상 전량 전송"은 그 자체로 일관된다.
  **진짜 원인은 에디터가 한 번도 로드하지 않은 상태를 "빈 값"으로 단정하는 것**(`loaded` 플래그 부재) →
  수정 방향은 "status처럼 비교 가드"가 아니라 **"로드 전/실패 시 정산 키를 빼거나 저장을 막기"**.
- ✅ 감사자가 놓친 부분 방어: `api.ts`가 **GET만 5xx에 3회 재시도**한다(비-5xx·네트워크 단절·401은 대상 아님).
  단 재시도가 도는 동안 "미완료 창"은 오히려 넓어진다.

**현재 폭발 반경 0**(`customer_deliveries` 1행 · `fee_amount` NULL · 비용 0건). 값이 쌓이면 노출되는 잠복 결함.
🎁 같은 `loaded` 게이트 부재의 **거울면**: 늦게 도착한 GET 응답이 **admin이 입력 중이던 값을 덮는다** — 같은 수정으로 함께 닫힌다.

## C1 — canonical_name 스테일 (ADJUSTED · 상 → 하~중) ⚠️ 강등 근거를 반드시 읽을 것

`updateTrim`이 `trimName` 변경 시 `name`만 동기화하고 `canonical_name`(파생값)은 손대지 않는다.
**실측 71행 불일치**(공백 정규화 후 · mc_code 보유 68) — 숫자 자체는 적대 검증이 정확히 재현했다.

**그런데 피해 논거가 두 곳 다 무너졌다**
- **파트너(제프)**: 회신 §②의 매칭 규약 = `masterMcCode` 링크 있으면 **파트너가 그 offering의 (브랜드, 모델명)으로 치환** 후 계산.
  `modelName` 매칭은 mcCode를 **안 실을 때만** 탄다. CRM은 서버 zod `masterMcCode: min(1)` 강제 + 픽커가
  `quotable = mcCode != null`로 선택 차단 → **계산에 미치는 해 0에 수렴**.
- **트림 선택 다이얼로그**: 호출부 둘 다 `accordion={false}`라 canonical을 쓰는 `buildGroupKey`가 **실행되지 않는다**.
  행 라벨도 `t.trimName ?? source`인데 **`trim_name` NULL/빈값이 1869행 중 0건**이라 폴백이 안 탄다.
- **앱**: 표시가 `trimName ?? canonicalName ?? name`이라 앱 화면에 stale이 뜰 경로 없음.

**잘못된 차량·금액이 나간 사례는 하나도 실증되지 않았다.**

**원인 귀속도 2.2배 과장** — 71건 중 승인 워크플로 기인은 **32건**뿐이고,
**34건은 모델 개명(`updateModel`)·트림 이동(`moveTrims`)** 기인이다(감사자가 못 본 더 큰 축). 나머지 5건은 그 밖.
→ `updateTrim`만 고치면 **절반만 잡힌다.**

**남는 실해**: ⓐ MC 마스터 `TrimEditPanel`의 `정규화명 (자동 생성)` read-only 표시에 stale 문자열
ⓑ **앱 검색 풀 오염**(앱이 `trim_name/canonical_name/name` 3열 OR 검색 — 옛 이름으로도 걸리는 오탐) ⓒ 공유 컬럼을 CRM이 썩히는 계약 문제.

**후속 조사 정정(2026-08-06 오후 · 유슨생 세션 — 강등 자체는 유지)**: "앱 화면에 stale이 뜰 경로 없음"은
**고객 화면 기준**으로만 정확하다 — 앱 관리자 `trim_options_panel.dart` 서브타이틀 1곳은 폴백이 **canonical
1순위**라 stale이 보인다(관리자 전용이라 심각도 불변). 덧붙여 앱 Edge `search_trims`는 `.or()`에만 canonical을
넣고 SELECT 상수(`TRIM_SELECT_WITH_MODEL_BRAND`)에서 빠져 **후필터에서 canonical 매칭분이 탈락**한다(앱 몫
parity 구멍 — stale 노출과 반대 방향). 실측 71/68은 "올바른 국산/수입 분기 + 완전 공백 정규화" 판정으로 재현
확정(원문 비교 103 · 후행 공백만 30 — 2025-12-25 벌크 임포트 잔재). **기원**: 앱은 read-only 전환(앱 #394,
2026-06-18) 전까지 트림 수정 시 canonical을 재조립했다 — CRM 이관 때 그 재계산이 이식 누락된 것.

**부수 발견**: `catalog-admin.ts:moveTrims` 주석이 "trim_code/mc_code/**canonical_name**은 트리거가 변경을 막아 유지"라는데,
`catalog.prevent_trim_code_change()` 실체는 `trim_code`·`mc_code` **둘만** 검사한다 → **주석이 거짓**.

## C2 — 전체 승인 broadcast 팬아웃 (ADJUSTED · 중)

`approveChangeRequestById`가 건마다 `notifyQueueUpdated()` + `broadcastCatalogQueueChanged({applied:true})`를 부른다.
`handleApproveAll`의 주석("재조회는 끝에 한 번만 — 건마다 걸면 카탈로그를 144번 다시 읽는다")이 실제로 아끼는 건
**카탈로그 3종뿐**이고 큐·gaps·모델 pending은 그대로 건별로 나간다.

**적대 검증의 정정**: 🔴 **승인하는 본인 세션도 같은 팬아웃을 문다**(144건에 290~430 요청 — 상대 세션 유무와 **무관하게 항상**).
원 주장이 "상대 세션"으로 한정한 탓에 이 축을 빠뜨렸다. 반면 형태는 "폭발"이 아니라 **1분 내외 지속 드립**이고,
전부 GET이라 **데이터 파손·중복 승인 0**. 디바운스·rate limit 반박은 실패(`createQueueEpochFetch`는 같은 epoch 안만 합치는데
broadcast 1건이 epoch를 1 올려 **메시지 간 합류가 원천 불가**).

⚠️ **고칠 때 주의**: 벌크 동안 신호를 **억제**하면 실패 건이 섞일 때 "큐가 안 줄어든 것처럼 보이는" 배지 stale이 생긴다 —

## P2 — app_user_id 스크럽 미구현 (ADJUSTED · 하)

미구현은 사실(코드 4각도 + `cron.job` 전수 확인 — CRM용 스크럽 잡 없음. `process-account-deletions`는 **앱 팀 Edge Function** 호출이라 무관).
**그러나 원 주장의 원인·범위가 틀렸다**:
- 감사자가 근거로 든 **"앱 팀 회신 §2a"라는 절이 존재하지 않는다.** 회신은 스크럽을 약속한 적이 없고 앱 팀도 요구한 적 없다
  → **외부 계약 위반이 아니다.** 실제 출처는 구현 스펙 §2a(CRM 내부 계획)이고, 그 편승 대상(`§6 정리 잡`)도 **dangling**이다(§6은 "테스트 주의").
- **기능 영향 0.** 남는 건 개인정보 최소화 자기 약속의 미이행 + `customer_deletions`와의 비대칭(같은 식별자를 한쪽은 지우기로 결정·구현).

→ 최소 조치는 **주석을 계획형으로 정정 + 인용을 `spec §2a`로 교정**. 지금 상태(주석은 "한다"·코드는 안 함)만은 남기면 안 된다.

## 🔴 진짜 발견 — 권한·파기·돈의 서버 그물이 전부 CI 밖

두 변이 앵글이 **독립적으로 같은 결론**에 도달했다. 개별 결함보다 이쪽이 이번 감사의 본체다.

- 파기 관련 그물 14개 중 **10개가 `db-bound-tests.ts` registry에 등재** → `test:pure`에서 제외 → 로컬 `test:server`에서만 돈다.
  `vitest.config.ts` include가 `client/src/**`+`test/**`뿐이라 **서버 파기 코드의 `test:unit` 커버리지는 구조적으로 0**.
- **"그물이 있다"와 "PR이 빨개진다"는 다른 말이다.**

**심각도 상 3건 — `WHERE` 절을 지웠는데 CI 8단계 전량 통과**
| 변이 | 실제로 일어나면 |
|---|---|
| `purgeCustomerCore`의 고객 DELETE에서 WHERE 제거 | **전 고객 삭제**(CASCADE로 자식 7종·임베딩·서류까지) |
| `listRetentionDueCustomers`의 retention 필터 제거 | **전 고객 수렴 파기** — 사람 조작 없이 **크론이 자동 발화** |
| `deleteDealerProposals`의 dealerUserId 필터 제거 | **전 딜러 제안 삭제** |

**A2-b가 찾은 CI 밖 그물 5건**(전부 상): 승인 드리프트 차단(409) 제거 · 승인 권한 admin→+manager(**팀장이 자기 요청 승인**) ·
정산 라우트 권한 개방 · **정산 마스킹 role 하드코딩**(전 역할 응답에 정산이 실림) · `updated_at` 앱 시계 전환.
→ 정산 마스킹은 **설계 문서가 스스로 인정한 공백**이다: 주석이 "로직은 순수 테스트(CI)가, **배선**은 이 파일이 잠근다"는데 그 "이 파일"이 CI 밖.
