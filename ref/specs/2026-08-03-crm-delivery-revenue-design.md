# 출고 기준 실적 지표 — 구현 스펙 (2026-08-03)

> 경영 리포트 히어로 3지표(전체 출고·리스 실적·렌트 실적)를 목업에서 실데이터로 바꾼다.
> 2026-08-02 리포트 실데이터화(#428)가 "실적 인식 기준 미합의"로 남겨둔 부분이고, 이사님 확정으로 열렸다.

## 1. 이사님 확정 (2026-08-03)

**최초 회신은 "입금 달 기준"이었으나 같은 날 정정됐다. 아래가 최종이다.**

- **실적·대수는 전부 계약 확정 달 기준.** ⚠️ **차량 인도일이 아니다**(2026-08-03 2차 정정).
- **입금은 CRM 지표가 아니다** — 경영 쪽에서 별도 관리한다(회계 범주).
- **슬라이딩 수수료는 출고 건당 1건**, 보통 출고 다음 달에 1회 정산된다.

### 1b. "출고"라는 말이 두 사건을 가리킨다 (⚠️ 이 문서에서 가장 중요한 함정)

이사님 회신이 두 번 정정된 이유이자, **실제로 잘못 구현했다가 되돌린 지점**이다(#432 → #436).

| 사건 | 뜻 | 컬럼 | 실적 |
|---|---|---|---|
| 차량 인도 | 고객이 차를 받는 날 | `delivered_date` | ✗ |
| **계약 확정** | 인도 후 상담사가 고객·금융사 사이에서 URL 인증·해피콜을 마무리 → **수수료 집계 시작** | `contract_confirmed_date` | ✅ |

- **현장에서는 실적을 말할 때 이 확정을 그냥 "출고"라고 부른다**("7월 출고 86대"). 그래서 화면 라벨은
  "전체 출고"를 유지하되(실무 직관), **코드에서는 두 날짜를 반드시 구분**한다.
- 간격은 보통 **당일~일주일**. 월을 넘기면 **확정된 달**의 실적이다(7월 출고·8월 확정 = 8월 실적).
- **취소·지연은 이 구간에서만 생긴다** — 차량 문제(인수 거부·교체)면 계약 유지·확정 지연, 계약 문제면
  출고 → 계약취소로 확정까지 못 간다. 고객이 해피콜을 안 받는 경우는 실무상 없다.
- 확정을 입력하는 주체는 **담당 상담사**다(금융사 통보가 아니라 고객 소통의 마지막 단계).
- ⚠️ **확정 이후에는 조건이 바뀌지 않는다** → 실적 금액을 스냅샷으로 굳힐 필요가 없다(§3b 갱신).

### 1a. 실적과 매출은 다른 축이다

| 구매방식 | 실적(취급 규모) | 매출(회사 수입) |
|---|---|---|
| 운용리스 | **취득원가** | 슬라이딩 수수료(실적의 1% 내외) |
| 장기렌트 | **최종 차량가** | 슬라이딩 수수료 |
| 할부 | **개념 없음** | 실입금액 자체 |
| 중고리스 | **개념 없음** | 실입금액 자체 |

할부·중고리스는 실적이 **0이 아니라 집계 대상이 아니다.** 히어로에 "리스 실적/렌트 실적"만 있고
할부 칸이 없는 현재 구조가 이 개념과 일치한다. **단 출고 대수에는 포함된다**(전 구매방식의 출고 대수).

이번 슬라이스는 **실적 축만** 다룬다. 매출 축(수수료·실입금액)은 §6.

## 2. 산식 — 이미 저장돼 있다

```
최종 차량가 = 기본가 + 옵션가 − 할인            → 장기렌트 실적
취득원가   = 최종 차량가 + 등록비용(취득세·공채·탁송·부대)  → 운용리스 실적
```

`quote-pricing.ts`의 `computePricing`이 그대로 이 식이고(이사님 정의와 문자 그대로 일치),
결과는 `crm.quotes.final_vehicle_price` · `acquisition_cost`에 **전 견적 32/32 저장돼 있다**(2026-08-03 실측).
**새로 계산할 것이 없다.**

## 3. 지표 정의

| 지표 | 정의 |
|---|---|
| 전체 출고 | `customer_deliveries.contract_confirmed_date` ∈ 월 인 건수 (**전 구매방식**) |
| 리스 실적 | 그중 구매방식 `운용리스`인 건의 `acquisition_cost` 합 |
| 렌트 실적 | 그중 구매방식 `장기렌트`인 건의 `final_vehicle_price` 합 |

셋 다 전월 대비 델타를 함께 낸다(화면이 "+15 전월 대비" 형태).

### 3a. 원천 — 왜 `contract_confirmed_date`인가

**실적이 인정되는 시점이 계약 확정이기 때문**이다(§1b). 참고로 다른 출고 신호는 월 집계에 쓸 수 없다 —
`customers.status='출고완료'`는 날짜가 없고, 출고 예정 일정은 실측일이 아니다.

| 신호 | 2026-08-03 실측 | 실적 |
|---|---|---|
| `customers.status = '출고완료'` | 4건 | ❌ 날짜가 없어 월 집계 불가 |
| `customer_deliveries.delivered_date`(차량 인도) | 1건 | ❌ 확정 전이라 수수료 미집계 |
| **`customer_deliveries.contract_confirmed_date`** | **0건**(신설) | ✅ |
| `customer_schedules.type='출고' AND done` | 0건 | ❌ 예정 일정이라 실측일이 아님 |

⚠️ **신호들이 서로 어긋나 있다.** 상태가 출고완료인 4명은 날짜가 비어 있고, 인도일이 있는 유일한
1건(제임스 7/31)은 상태가 아직 `딜러사계약중`이다. 코드 문제가 아니라 **날짜 입력이 운영에 정착되지
않은 것**이고, 확정일이 채워지기 전까지 이 지표는 0을 표시한다(§5). 신설 컬럼이라 **당분간 전부 0이
정상**이다.

### 3b. 구매방식·금액의 출처

그 고객의 **계약 진행 견적**(`decision_status='contracting'`)에서 파생한다. 구매방식은 대표 시나리오
(`primary_scenario_id`) 경유 — `contractingQuoteSummary`(queries/customers.ts)가 이미 쓰는 것과 **같은 축**이다.
고객당 contracting 견적은 최대 1개임을 실측으로 확인했다(중복 0).

**스냅샷을 두지 않는다**(2026-08-03 정정). 처음엔 "견적을 수정하면 지난달 실적이 소급해서 바뀐다"를
걱정해 스냅샷을 계획했는데, **계약 확정 이후에는 조건이 바뀌지 않는다**는 것이 확인되면서(이사님)
그 창이 원리적으로 닫혔다. 파생이 항상 정확하므로 컬럼을 늘릴 이유가 없다.
⚠️ 남는 유일한 경로는 **계약 진행 견적 자체를 삭제**하는 경우다(실적이 사라진다). 실제로 발생하면
그때 스냅샷을 도입한다 — 지금 넣으면 쓰지 않을 컬럼이 하나 늘 뿐이다.

## 4. API

`GET /api/reports/admin`(admin 단독, 2026-08-02 spec §3) 응답에 `delivery`를 추가한다.

```jsonc
"delivery": {
  "count": 1, "prevCount": 0,
  "leaseAmount": 57000000, "prevLeaseAmount": 0,
  "rentAmount": 0, "prevRentAmount": 0
}
```

기간 지표라 **월 스코프가 정상 작동한다**(스냅샷 지표인 `inProgress`·`contracted`와 다르다).

## 5. 화면

히어로 3칩이 실데이터가 되고 **"샘플" 배지가 빠진다**. **칩 라벨은 "전체 출고" 그대로**다 —
현장에서 실적을 말할 때 쓰는 말이고(§1b), 기준만 확정일이다. 값이 0일 때가 당분간 정상이므로
**계약 확정일이 입력돼야 집계된다는 사실을 화면에 알린다** — 숫자가 0인 것과 기능이 고장난 것을
구분하지 못하면 "리포트가 안 나온다"로 읽힌다.

출고 정보 팝오버에는 **"출고 실측일"과 "계약 확정일"이 나란히** 놓인다. 여기만 라벨을 구분하는
이유는 상담사가 두 값을 각각 채워야 하기 때문이다 — 집계만 보여주는 히어로와 달리 어느 칸에 뭘
넣을지가 명확해야 한다.

상단바(Topbar) 요약도 같은 값 계통이지만 **이번 범위가 아니다** — 그쪽은 전 역할이 보는 자리라
admin 전용 리포트 API를 그대로 쓸 수 없다(권한 축이 다르다). 별도 슬라이스.

## 6. 매출 축 — ✅ 구현 완료(2026-08-03, 같은 날 후속)

**유슨생 결정**: ⓐ**admin 단독**(manager도 403) ⓑ**읽기도 차단** ⓒ**업무 AI 노출도 admin만**.

- `crm.customer_deliveries` += `settled_at`(입금일) · `fee_amount`(실입금액). 마이그 **0049**(additive).
  수수료가 **출고 건당 1건**이라(이사님) 고객당 1행 구조를 그대로 쓴다 — 분할 정산이 아니므로 별도 테이블 불요.
  한 컬럼이 두 경우를 담는다: 리스·렌트는 슬라이딩 수수료, 할부·중고리스는 실입금액 자체.
- **경계 4층**(테이블 분리 대신):
  1. **타입 분리** — `CustomerSettlement`를 `CustomerDeliveryInfo`와 따로 둔다. 섞으면 비admin 저장이
     정산을 빈 값으로 덮는다.
  2. **목록 응답 미포함** — 출고 정보 jsonb는 필드 명시 조립이라 정산이 실리지 않는다 = 읽기 차단.
  3. **별도 라우트 + `requireRoles(["admin"])`** — `GET/PUT /api/customers/:id/settlement`.
  4. **tripwire** — `customers.settlement-exposure.test.ts`가 목록 응답에 정산이 새면 실패시킨다.
     나중에 전체 컬럼 조립으로 바뀌면 조용히 새는 부류라 그물이 필요하다.
- **업무 AI는 지금도 노출 0**이다 — 정산을 조회하는 도구가 없다. 나중에 추가할 때 admin scope를 걸어야 한다.
- ⚠️ **차단 코드가 role마다 다르다**(게이트 다층): manager는 `requireRoles`가 403, staff·dealer는
  role scope(#301)가 먼저 404(존재 비노출), dealer PUT은 dealerWriteGate가 403. 테스트는 manager 403을
  핵심으로 잡고 나머지는 "200 아님"으로 단언한다.
- **UI**: 출고 정보 팝오버 하단에 admin에게만 정산 섹션. 저장은 출고 → 정산 순서로 두 번 호출한다
  (정산이 먼저 가면 계약 정보가 빈 행을 만든다). 정산만 실패하면 부분 성공을 정직하게 알린다.

### 6a. 아직 안 한 것

  살리면 반쪽 화면이 된다. 비용은 항목이 여럿(시공비·탁송비)이라 구조 결정이 필요하고, 마진은 파생이다.
