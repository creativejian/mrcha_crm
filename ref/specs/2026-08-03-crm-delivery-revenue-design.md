# 출고 기준 실적 지표 — 구현 스펙 (2026-08-03)

> 경영 리포트 히어로 3지표(전체 출고·리스 실적·렌트 실적)를 목업에서 실데이터로 바꾼다.
> 2026-08-02 리포트 실데이터화(#428)가 "실적 인식 기준 미합의"로 남겨둔 부분이고, 이사님 확정으로 열렸다.

## 1. 이사님 확정 (2026-08-03)

**최초 회신은 "입금 달 기준"이었으나 같은 날 정정됐다. 아래가 최종이다.**

- **실적·대수는 전부 출고 달 기준.** 3월 계약 → 4월 출고 → 5월 입금인 건은 **4월 실적**이다.
- **입금은 CRM 지표가 아니다** — 경영 쪽에서 별도 관리한다. CRM 화면에 표기되는 대수·실적은 출고 기준.
- **슬라이딩 수수료는 출고 건당 1건**, 보통 출고 다음 달에 1회 정산된다.

### 1a. 실적과 매출은 다른 축이다

| 구매방식 | 실적(취급 규모) | 매출(회사 수입) |
|---|---|---|
| 운용리스 | **취득원가** | 슬라이딩 수수료(실적의 1% 내외) |
| 장기렌트 | **최종 차량가** | 슬라이딩 수수료 |
| 할부 | **개념 없음** | 실입금액 자체 |
| 중고리스 | **개념 없음** | 실입금액 자체 |

할부·중고리스는 실적이 **0이 아니라 집계 대상이 아니다.** 히어로에 "리스 실적/렌트 실적"만 있고
할부 칸이 없는 현재 구조가 이 개념과 일치한다. **단 출고 대수에는 포함된다**(전 구매방식의 출고 대수).

이번 슬라이스는 **실적 축만** 다룬다. 매출 축(수수료·실입금액)은 §6.

## 2. 산식 — 이미 저장돼 있다

```
최종 차량가 = 기본가 + 옵션가 − 할인            → 장기렌트 실적
취득원가   = 최종 차량가 + 등록비용(취득세·공채·탁송·부대)  → 운용리스 실적
```

`quote-pricing.ts`의 `computePricing`이 그대로 이 식이고(이사님 정의와 문자 그대로 일치),
결과는 `crm.quotes.final_vehicle_price` · `acquisition_cost`에 **전 견적 32/32 저장돼 있다**(2026-08-03 실측).
**새로 계산할 것이 없다.**

## 3. 지표 정의

| 지표 | 정의 |
|---|---|
| 전체 출고 | `customer_deliveries.delivered_date` ∈ 월 인 건수 (**전 구매방식**) |
| 리스 실적 | 그중 구매방식 `운용리스`인 건의 `acquisition_cost` 합 |
| 렌트 실적 | 그중 구매방식 `장기렌트`인 건의 `final_vehicle_price` 합 |

셋 다 전월 대비 델타를 함께 낸다(화면이 "+15 전월 대비" 형태).

### 3a. 원천 — 왜 `delivered_date`인가

출고 신호가 셋인데 **월 집계가 가능한 것은 `delivered_date` 하나뿐**이다.

| 신호 | 2026-08-03 실측 | 월 집계 |
|---|---|---|
| `customers.status = '출고완료'` | 4건 | ❌ 날짜가 없다 |
| `customer_deliveries.delivered_date` | **1건** | ✅ |
| `customer_schedules.type='출고' AND done` | 0건 | (예정 일정이라 실측일이 아님) |

⚠️ **세 신호가 서로 어긋나 있다.** 상태가 출고완료인 4명은 출고일이 비어 있고, 출고일이 있는
유일한 1건(제임스 7/31)은 상태가 아직 `딜러사계약중`이다. 코드 문제가 아니라 **출고 실측일 입력이
운영에 정착되지 않은 것**이고, 그게 채워지기 전까지 이 지표는 사실상 0을 표시한다(§5).

### 3b. 구매방식·금액의 출처

그 고객의 **계약 진행 견적**(`decision_status='contracting'`)에서 파생한다. 구매방식은 대표 시나리오
(`primary_scenario_id`) 경유 — `contractingQuoteSummary`(queries/customers.ts)가 이미 쓰는 것과 **같은 축**이다.
고객당 contracting 견적은 최대 1개임을 실측으로 확인했다(중복 0).

⚠️ **한계(의도된 트레이드오프)**: 파생이라 **견적을 나중에 수정하면 지난달 실적이 소급해서 바뀐다.**
지금은 출고 건이 1건이라 실질 위험이 0이라 파생으로 간다. 매출 축(§6)에서 정산 컬럼을 추가할 때
**출고 시점 금액 스냅샷**을 함께 도입해 이 창을 닫는다 — 마이그레이션을 한 번으로 묶기 위해서다.

## 4. API

`GET /api/reports/admin`(admin 단독, 2026-08-02 spec §3) 응답에 `delivery`를 추가한다.

```jsonc
"delivery": {
  "count": 1, "prevCount": 0,
  "leaseAmount": 57000000, "prevLeaseAmount": 0,
  "rentAmount": 0, "prevRentAmount": 0
}
```

기간 지표라 **월 스코프가 정상 작동한다**(스냅샷 지표인 `inProgress`·`contracted`와 다르다).

## 5. 화면

히어로 3칩이 실데이터가 되고 **"샘플" 배지가 빠진다**. 다만 값이 0일 때가 당분간 정상이므로,
**출고 실측일이 입력돼야 집계된다는 사실을 화면에 알린다** — 숫자가 0인 것과 기능이 고장난 것을
구분하지 못하면 "리포트가 안 나온다"로 읽힌다.

상단바(Topbar) 요약도 같은 값 계통이지만 **이번 범위가 아니다** — 그쪽은 전 역할이 보는 자리라
admin 전용 리포트 API를 그대로 쓸 수 없다(권한 축이 다르다). 별도 슬라이스.

## 6. 다음 슬라이스 — 매출 축

- `crm.customer_deliveries` += 입금일 · 실입금액(수수료) · 실적 금액 스냅샷.
- 수수료가 **출고 건당 1건**으로 확정돼(이사님) 고객당 1행 구조를 그대로 쓴다. 분할 정산이 아니므로
  별도 테이블이 필요 없다.
- 정산은 **관리자만** 보고 쓰게 한다(유슨생 요구). 결정 대기 3건: ⓐ관리자 범위(admin 단독 vs manager 포함)
  ⓑ읽기도 막을지(상담사가 본인 건 수수료를 못 보는 게 맞는지) ⓒ업무 AI 노출 여부.
- 노출 경계는 테이블 분리가 아니라 **타입·목록 응답·API 게이트·tripwire 테스트 네 층**으로 만든다
  (같은 테이블로도 충분함을 확인했다 — 저장은 전달된 필드만 갱신하고, 목록 응답은 필드를 명시 조립한다).
