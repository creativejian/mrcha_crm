# CRM 키보드 단축키 설계 (2026-08-08)

> 유슨생 요청 — Supabase 대시보드의 `Keyboard shortcuts` 패널을 CRM에 도입한다.
> 범위는 **전역 액션 + 네비게이션**, role 스코프를 사이드바와 동일하게 적용한다.

## 1. 목표

- `?` 한 키로 **검색 가능한 단축키 패널**을 연다(표기는 `⇧?`).
- 자주 쓰는 화면·도구를 마우스 없이 연다.
- **보이지 않는 메뉴는 열리지도 않는다** — 단축키가 사이드바 role 게이트를 우회하는 뒷문이 되면 안 된다.

## 2. 키 배정 (SSOT — 구현은 이 표를 따른다)

### 2.1 전역 액션

| 키 | 액션 | 표기 | 노출 |
|---|---|---|---|
| `?` | 단축키 패널 열기 | `⇧?` | 전원 |
| `⌘K` | 고객 통합 검색 | `⌘K` | 딜러 제외 |
| `⌘I` | 업무 AI 패널 | `⌘I` | 딜러 제외 |
| `⌘E` | 계산기 | `⌘E` | 딜러 제외 |
| `⌘B` | 사이드바 접기/펴기 | `⌘B` | 전원 |
| `O` `N` | 알림 | `O then N` | 딜러 제외 |

- **딜러 제외 4종의 근거**: 딜러 상단바는 내부 업무 도구 5종(검색·업무 AI·계산기·상담 대기·알림)을
  **렌더하지 않는다**(2026-08-02 유슨생 — 구 disabled 회색 노출을 미표시로 전환). 화면에 없는 것을
  키로 여는 것은 그 결정을 되돌리는 셈이다.
- **`⌘K`**: Safari에서 Supabase가 정상 동작함을 유슨생이 실기 확인(2026-08-08).
- **`⌘E`**: 주요 브라우저에 기본 동작이 없다. `⌘J`(Chrome 다운로드)·`⌘D`(북마크)는 피했다.
- **알림만 시퀀스인 이유**: 빈도가 낮다. Supabase도 `O then C`(Open Connect sheet)를 같은 이유로 쓴다.

### 2.2 네비게이션 — `G` then `X`

**전원(딜러 제외)**

| 키 | 목적지 | 경로 |
|---|---|---|
| `G` `H` | 대시보드 | `/` |
| `G` `T` | 실시간 상담 | `/chat` |
| `G` `C` | 고객 관리 · 전체 보기 | `/customers` |
| `G` `N` | 고객 관리 · 상담 필요 | `/customers?view=consulting` |
| `G` `K` | 고객 관리 · 계약 관리 | `/customers?view=contract` |
| `G` `D` | 고객 관리 · 출고 관리 | `/customers?view=delivery` |
| `G` `E` | 고객 관리 · 출고 정산 | `/customers?view=settlement` |
| `G` `B` | 고객 관리 · 보류 / 이탈 | `/customers?view=hold` |
| `G` `P` | 상담 파이프라인 | `/pipeline` |

**admin · manager**: `G` `Q` 앱 견적요청 · `G` `A` 상담사 배정 · `G` `I` 상담 신청 · `G` `O` 팀원 관리 · `G` `M` MC 마스터
**admin**: `G` `R` 경영 리포트 · `G` `F` 재무 관리
**딜러**: `G` `M` **할인 업데이트**(→ `/mc-master`)

- ⚠️ **`H`는 대시보드다.** 보류/이탈(Hold)이 아니다 — Supabase가 `G then H`를 Project Overview에
  주는 관례를 따랐고, 보류/이탈은 `B`(보류)로 옮겼다. 초안에서 실제로 충돌했던 자리다.
- ⚠️ **`G` `M`은 role에 따라 라벨이 다르다** — 내부 직원 "MC 마스터", 딜러 "할인 업데이트".
  같은 `/mc-master`인데 딜러 포털의 명칭이 다르기 때문이다(`dealerMenuItems`). 레지스트리는
  목적지가 아니라 **표시 라벨을 role별로 해석**해야 한다.
- **고객 관리 서브탭을 최상위 시퀀스에 편입한 근거**(유슨생 결정): 실무 진입 빈도가 화면 단위와
  같은데 3단계(`G` `C` `N`)로 내리면 입력이 3회가 되고 중간 상태·타임아웃 설계가 복잡해진다.
  Supabase도 Table Editor·SQL Editor처럼 하위 개념에 최상위 문자를 준다.

### 2.3 단축키를 주지 않는 것

**딜러 메뉴 중 목적지 없는 3개**(대시보드 · 고객 관리 · 재고 업로드). `dealerMenuItems`의 세 번째
원소가 없어 화면이 아직 존재하지 않는다. 사이드바가 이미 같은 이유로 `disabled` 처리하며 근거를
주석에 남겼다:

> 목적지 없는 항목은 disabled로 둔다: **눌리는데 아무 일도 안 일어나는 버튼이 더 나쁘다**

키에도 같은 논리를 적용한다 — 아무 일도 안 일어나는 단축키는 버튼보다 나쁘다(왜 안 되는지 화면에
단서가 없다). 🔵 그 3개는 `ref/director-pending-confirmations.md` 항목 30으로 이사님 판단 대기 중이고,
**화면이 생기면 자동으로 단축키가 붙는다**(아래 §3.2 SSOT 구조 덕분).

## 3. 구조

```
client/src/lib/keyboard-shortcuts.ts       레지스트리(순수 데이터) + role 필터 + 시퀀스 매칭
client/src/lib/nav-visibility.ts           role별 메뉴 가시성 SSOT (신규 — 사이드바와 공유)
client/src/hooks/useKeyboardShortcuts.ts   전역 리스너 (판정은 전부 위임하는 껍데기)
client/src/components/KeyboardShortcutsPanel.tsx   패널 UI (검색 필터)
```

### 3.1 훅은 Topbar에 건다

전역 액션 4종의 상태(`globalSearchOpen`·`workAiOpen`·`notificationsOpen`, 계산기 모달)를 **Topbar가
소유**하고, Topbar는 이미 `roleTab`·`onToggleSidebar` prop을 받는다. App에 훅을 걸면 그 상태들을
끌어올리거나 ref로 노출해야 해서 비용이 크다.

**네비게이션만 App에 위임**한다 — Topbar에서 `useNavigate`를 직접 부르지 않고 App이 새 prop
`onShortcutNavigate(path: string)`를 내려준다(App이 라우팅을 소유하는 기존 구조 유지). 경로 생성은
이미 있는 순수 함수를 재사용한다: `VIEW_TO_PATH`(App) · `customerListPath`(`lib/customer-route.ts`).

패널 UI도 Topbar 안에 렌더한다 — 기존 팝오버 4종(통합검색·알림·계정설정·확인모달)과 같은 층이고
공용 훅 `usePopoverDismiss`(Esc·외부클릭)를 그대로 쓴다.

### 3.2 ⚠️ role 가시성 SSOT 추출 (이 설계의 핵심 리스크)

현재 `canViewAdminMenu`·`canViewTeamMenu`는 `Sidebar.tsx:144`에서 **로컬 계산**된다. 단축키가 이걸
독자적으로 다시 계산하면, 메뉴 권한이 바뀔 때 **한쪽만 고쳐져 "화면엔 없는데 키로는 열리는" 뒷문**이
생긴다. 서버가 403으로 막더라도 그건 데이터 방어지 UI 정합이 아니다.

그래서 **가시성 판정을 `lib/nav-visibility.ts`로 먼저 추출하고 사이드바가 그것을 쓰도록 바꾼 뒤**,
단축키 레지스트리도 같은 모듈을 import한다. 이 저장소가 파리티를 다루는 방식(공유 순수 SSOT +
드리프트 테스트 — `doc-type-parity`·`roles-parity` 선례)과 같다.

**즉 이 작업은 사이드바를 건드린다.** 순수 추출이라 동작 변경은 0이어야 하고, 기존 사이드바 테스트가
무수정으로 통과하는 것이 그 증거다.

### 3.3 레지스트리 형태

```ts
type Shortcut = {
  id: string;              // 안정 식별자(테스트·드리프트 대조 키)
  keys: string[];          // ["g","c"] 시퀀스 | ["mod","k"] 조합
  group: "global" | "navigation";
  path?: string;           // 네비게이션 목적지(순수 데이터)
  action?: GlobalActionId; // 전역 액션 식별자
  label: (role: RoleTab) => string;  // role별 라벨(§2.2 딜러 예외)
};
```

`label`이 함수인 유일한 이유는 `G` `M`의 role별 명칭 차이다. 그 외는 상수를 반환한다.

## 3.4 ⚠️ 한글 입력 모드 — `event.key`가 아니라 `event.code`로 읽는다

유슨생 질의(2026-08-08): *"한글로 되어 있을 때는 안 되는 거지?"* — 키 종류마다 다르다.

| 키 | 한글 모드 | 근거 |
|---|---|---|
| `⌘K`·`⌘I`·`⌘E`·`⌘B` | **동작** | macOS에서 Command 조합은 IME를 우회한다 |
| `?` | **동작** | 문장부호는 IME가 그대로 통과시킨다(`Shift+/`) |
| `G` `H` 시퀀스 | **`event.key`로 읽으면 죽는다** | `g` → `"ㅎ"`으로 잡혀 매칭이 실패한다 |

**그래서 시퀀스·단일 문자 판정은 `event.code`(물리 키 위치)를 1차로 읽는다.**

```
event.key  → "ㅎ"     입력 모드에 따라 변한다
event.code → "KeyG"   물리 키라 입력 모드와 무관하다
```

Linear·GitHub이 쓰는 방식이다. **대가**: `event.code`는 물리 레이아웃 기준이라 Dvorak·AZERTY에서
어긋난다 — 사용자가 전원 한국어 QWERTY라 실질 영향 0으로 보고 수용한다.

`?`는 물리 키가 `Slash`+Shift라 `code` 기준(`event.code === "Slash" && event.shiftKey`)으로 잡되,
`event.key === "?"`도 함께 허용한다(레이아웃 차이 흡수).

🔵 **실기 확인 필요** — Safari·Chrome × macOS 한글 입력기 조합은 브라우저마다 미묘한 차이가 있어
코드 논리만으로 단정하지 않는다. 구현 후 **한글 모드에서 `G` `H`·`?`·`⌘K` 3종을 실제로 눌러 확인**한다.

## 4. 안전장치

| # | 가드 | 이유 |
|---|---|---|
| 1 | `input`·`textarea`·`contentEditable` 포커스 중 무시 | 검색·메모·견적 입력 중 `g`가 화면을 바꾸면 안 된다 |
| 2 | **IME `isComposing` 가드** | 한글 조합 중 `keydown`이 조합 키로 발화한다. 선례 = `ChatComposer.tsx:40`·`AiAssistantPanel.tsx:163`. §3.4의 `event.code` 판정과 **함께** 쓴다 — code로 읽어도 조합 중 발화는 무시해야 한다 |
| 3 | modifier 동반 시 시퀀스 리셋 | `⌘G` 같은 조합이 시퀀스 중간 상태를 오염시키지 않게 |
| 4 | 시퀀스 타임아웃 **1.5초** | `G`만 누르고 방치하면 리셋 |
| 5 | 패널이 열려 있으면 다른 단축키 무시 | 패널 검색창 입력이 네비게이션을 발동시키지 않게(가드 1의 특수형) |

기존 전역 `keydown` 리스너는 **전부 `Escape` 전용**(`usePopoverDismiss` + 알림 패널)이라 문자 키와
축이 겹치지 않는다 — 충돌 0을 실측 확인했다(2026-08-08 전수 grep).

## 5. 테스트

**순수 단위**(전부 `test:unit`, CI 커버)

- **role별 노출 집합**: 딜러 3 · staff 15 · manager 20 · admin 22. 숫자만이 아니라 **id 집합**을 잠근다
- **시퀀스 매칭**: `G`→`C` 성공 · 타임아웃 리셋 · modifier 리셋 · 미등록 조합(`G`→`Z`) 무시
- **가드**: 입력 필드 포커스 · IME 조합 중 · 패널 열림 상태
- **한글 모드 매칭**(§3.4): `event.key === "ㅎ"`인데 `event.code === "KeyG"`인 이벤트가 `G`로
  매칭되는지. 이 케이스가 없으면 한글 사용자에게 시퀀스가 통째로 죽는데 영문 테스트는 전부 통과한다
- **드리프트 파리티**: 사이드바가 그리는 메뉴 집합 ↔ 단축키 네비게이션 집합 **양방향 대조**.
  한쪽에만 있으면 실패한다(메뉴가 늘었는데 단축키를 안 준 것도, 화면 없는 곳에 키를 준 것도 잡는다)
- **경로 유효성**: 모든 `path`가 `VIEW_TO_PATH` 또는 `customerListPath` 산출물과 일치

**변이 실증**(이 저장소 관례): 최소 3종을 주입해 RED를 실관찰하고 원복한다 —
①role 필터 제거(딜러가 전량 보임) ②IME 가드 제거 ③시퀀스 타임아웃 제거.

## 6. 범위 밖 (YAGNI)

- **사용자 정의 키 바인딩** — 저장소·충돌 해결 UI가 통째로 필요하다. 요청 없음
- **재무 관리 서브모드**(`financeListPath`) — `G` `F`로 기본 화면까지만. 서브탭 진입 빈도가 낮다
- **고객 상세**(`/customer-detail`) — 대상 고객이 지정돼야 의미가 있는 화면이라 전역 키에 안 맞는다
- **패널에서 키 직접 실행**(항목 클릭 = 이동) — 1차엔 목록·검색만. 필요해지면 추가

## 7. 확인 대기

**행위 변경 없음** — 기존 화면·동작을 바꾸지 않고 진입 수단만 추가한다. §3.2의 사이드바 리팩토링은
순수 추출이라 동작 변경 0이 요구사항이다. 따라서 `director-pending-confirmations` 등재 대상이 아니다.
