# 대표 견적요청(featured request) 기반 니즈 파생 — 설계

작성 2026-07-24 (유슨생·이사님 협의 확정) · 상태: **설계 확정 · 구현 미착수**
문제 정의 원본 = `ref/2026-07-24-customer-needs-staleness.md`

## 1. 배경

`crm.customers.need_*`는 최초 승격 때 한 번 시드되고 영원히 갱신되지 않는다. 앱 연결 고객은 니즈 카드가
앱 요청 목록으로 대체돼(`NeedsDashboard.tsx`의 `detail.appUserId` 분기) 상담사가 고칠 방법도 없다.
실측: 제임스는 요청 98건인데 니즈는 2026-03-05 첫 요청(`기아 레이`) 그대로이고, 오늘 하루에만 서로 다른
차 3대를 요청했다 — **"최신 요청 = 현재 관심"이라는 자동 갱신 가정 자체가 성립하지 않는다.**

그래서 **상담사가 요청 1건을 "대표"로 지정하고, 니즈는 그 요청에서 파생**한다.

## 2. 결정 사항

### D1. 대표 견적요청 개념

- 앱 연결 고객의 니즈는 **견적요청 1건(대표)에서 파생**된다.
- 기본 대표 = **최초 요청**(`created_at` 최소).
- 앱 카드 목록에 star(featured) 토글을 달아 상담사가 대표를 바꾼다. **항상 정확히 1건**이 대표다
  (라디오 성격 — 해제는 없고 다른 카드를 누르면 이동).
- 대표가 바뀌면 파생 7필드가 **한 트랜잭션에서 전부** 그 요청 기준으로 갱신된다.

### D2. 파생 7필드 (read-only)

| `need_*` 컬럼 | 화면 | 앱 소스 | 변환 |
|---|---|---|---|
| `need_model` | 목록 "차종" | `trim_id` → catalog 조인 | `브랜드 모델` |
| `need_trim` | 목록 트림줄 | 같음 | `trim_name` |
| `need_method` | 목록 "구매방식" · 상세 구매방식 | `payment_method` | `PAYMENT_METHOD_LABEL` |
| `need_contract_term` | 상세 계약기간 | `period` | `60` → `60개월` |
| `need_initial_cost` | 상세 초기비용 | `deposit_type`+`deposit_ratio`+`rental_deposit` | 아래 D2-a |
| `need_annual_mileage` | 상세 연간 주행거리 | `annual_mileage_km` | `20000` → `20,000km` |
| `need_timing` | 상세 출고 희망 시기 | `delivery_timing_mode`+`reference_month`+`target_month` | `deliveryTimingTextOf`(기존) |

- **값이 안 오면 빈칸으로 두고 수정도 막는다.** 앱은 구매방식·기간·보증금을 건너뛴 채 제출할 수 있다
  (실측: 2026-07-24 15:24 아반떼 N 요청이 그 3개가 전부 null). 빈 칸은 **정상 상태**다.
- ⚠️ **read-only 조건은 `app_user_id`가 아니라 `featured_request_id IS NOT NULL`이다.** 앱 연결
  고객인데 견적요청이 0건일 수 있다 — `createCustomerFromConsultation`(`consultations.ts:109`)이
  상담신청만으로도 `app_user_id`를 붙이고 `need_model`을 시드하기 때문이다(제임스는 상담신청도 45건).
  그 고객에게 `app_user_id` 기준으로 read-only를 걸면 파생 소스가 없는데 수기 입력도 막혀 **영원히 못
  채우는 고객**이 된다. 나중에 그 고객이 견적요청을 내면 그때 대표가 생기며 파생값이 수기값을 덮는다(D5).
- 앱 미연결 고객은 파생 소스가 없으므로 지금처럼 전부 수기 편집한다(전체 22명 중 20명).

**D2-a. 초기비용 변환** — 비율 우선, 금액은 폴백(`seedScenarioCardFromRequest`의 기존 규칙과 동일):

| 앱 값 | 저장 |
|---|---|
| `deposit_type='none'` | `무보증` |
| 유형 + `ratio>0` | `보증금 30%` / `선수금 20%` |
| 유형 + `ratio=0` + `amount>0` | `보증금 1,180만원` |
| 유형 + 둘 다 0 | `보증금` (유형명만) |
| 유형 null | 빈칸 |

⚠️ 앱카드 라벨(`depositLabelOf` — `보증금 (20%) 1,180만원` 병기)과 **형식이 다르다.** 상세 구매조건은
`parseInitialCost`가 읽는 CRM 어휘여야 앱 미연결 고객의 수기값과 같은 어휘가 된다. 복붙 금지.

**D2-b. 연간 주행거리** — 앱이 제출 전 검증하므로(`chat_quote_flow.dart:379` — 렌트 `{10000,20000,30000,40000}`,
그 외 `{10000,20000,30000}`) CRM CHECK 8종을 벗어나는 값은 오지 않는다. `annual_mileage_is_minimum`
(렌트+40000일 때만 true = "40,000km 이상")은 CRM 어휘에 대응이 없어 **버리고 `40,000km`로 매핑**한다.

### D3. 수기 편집 유지 (4필드)

`need_delivery_method`(인도 방식) · `need_contract_focus`(계약 포커스) · `need_customer_note`(고객 특이사항)
· `need_review_note`(심사 특이사항). 앱 연결 여부와 무관하게 편집 가능하다.

- 인도 방식·계약 포커스는 앱이 값을 **구조적으로 안 보낸다**(`delivery_method`·`quote_priority_codes`는
  UI 미노출 예약 필드 — 116건 전부 null/빈배열). 고객·심사 특이사항은 대응 앱 필드가 아예 없다.
- `need_colors`·`need_compare`·`need_memo`는 현행 유지(앱 연결 고객은 니즈 카드가 안 보여 편집 불가,
  파생 대상도 아님).

### D4. 출고 희망 시기 선택지를 앱과 통일

프리셋을 앱 UI와 같은 4종으로 교체한다 — `이번 달` · `다음 달` · **`3개월 이내`** · `미정`.
(제거: `좋은 조건 즉시` · `특정 월` 12개월 피커 — 앱이 예약 상태로 미노출.)

⚠️ **`3개월 이후`가 아니라 `3개월 이내`다**(`within_three_months`). 뜻이 반대라 그대로 옮기면 오독된다.

**저장 형식은 절대화를 유지한다**(계약 D3·D4, `quote-delivery.ts` "형식 변경 금지"). 상담사가 프리셋을
고르면 **고른 시점(오늘)을 참조월로** 절대화해 저장한다 — 2026-07에 `3개월 이내` 클릭 → `2026년 10월까지`.
상대 표현을 그대로 저장하면 같은 컬럼에 두 어휘가 섞이고, 시간이 지나면 그 값이 언제 기준인지 알 수 없어져
지금 고치려는 스테일 병이 그대로 재발한다.

### D5. 기존 값은 덮는다

마이그레이션 시점에 앱 연결 고객의 파생 7필드를 대표(=최초 요청) 값으로 **덮어쓴다**. 수기 유지 4필드는
건드리지 않는다.

근거: read-only 전환 후 남겨둔 수기값은 **상담사가 영원히 고칠 수 없는 값**이 된다. 파생값이면 star로
바꿀 수 있지만 옛 수기값은 그 수단조차 없고, 화면에서 둘이 구분되지 않아 출처를 아무도 모르는 혼합
상태가 된다. star 클릭 때는 어차피 덮어야 하므로 마이그레이션만 다르게 굴 이유가 없다.

⚠️ 대상은 현재 2명(김지안·제임스)이고 둘 다 목업/테스트 계정이라 실무 손실이 없다. 김지안의 수기값
(`장기렌트 · 금융리스 · 할부`, `보증금 30%` 등)은 최초 요청 값(`금융리스`, `보증금`)으로 대체된다.

### D6. 구현 방식 = 컬럼에 복사 (materialize)

`crm.customers.featured_request_id` 컬럼을 추가하고, 대표 지정/최초 승격 시 `need_*` 7개를 컬럼에 쓴다.

근거:
1. **`public.quote_requests`에 `updated_at`이 없다** — 앱이 제출한 요청은 불변 스냅샷이라 복사본이
   스테일해질 경로가 구조적으로 없다. 값이 변하는 건 우리가 star를 누를 때뿐이다.
2. 소비처 4곳(고객 목록 쿼리 · 차종 검색 · AI 프로필 청크 `buildCustomerProfileChunkText` · 상세)이
   전부 컬럼을 읽고 있어 **전부 무변경**으로 끝난다.
3. 임베딩 재백필 훅이 컬럼 변경 기준이라 그대로 돈다.

read-through 조인(`phone`의 `coalesce(profiles.phone_number, …)` 선례)은 얻는 것(스테일 방지)이 1로
이미 보장되는데 7필드 × 4소비처의 쿼리 수정 비용만 남아 기각.

### D7. read-only 강제는 API에서

컬럼은 그대로 `text`라 DB가 막아주지 않는다. `routes/customers.ts`의 PATCH에서 **`featured_request_id`가
있는 고객의 파생 7필드 쓰기를 409로 거부**한다(`phone`의 앱 연결 고객 409와 같은 형태). UI 비활성화만으로는
우회된다. 대표 지정 API(D1)는 이 거부를 우회하는 유일한 경로다.

## 3. 파급

- **AI 프로필 청크 재임베딩** — `need_*`가 바뀌면 `buildCustomerProfileChunkText` 출력이 달라져
  `embeddingContentHash`가 변한다. 백필을 **실행해야** 반영된다(자동 아님).
- **승격 시드 규칙 변경** — `fillNeedTimingIfEmpty`의 "빈 칸일 때만"(계약 D5 비파괴)이 대표 기반
  덮어쓰기로 바뀐다. 신규 승격은 최초 요청이 곧 대표라 결과가 같지만, **이미 연결된 고객에게 새 요청이
  와도 니즈는 안 바뀐다**(대표가 그대로이므로) — 이게 의도다.
- **`updated_at`은 `sql\`now()\``로** 찍는다(2026-07-23 `#334`·`#335`).

## 4. 구현 순서 (PR 3개)

1. **PR ①** — `featured_request_id` 마이그레이션 + 파생 규칙 순수 모듈 + 승격 시드 개편 + 기존 2명 백필.
   이것만 나가도 신규 승격이 즉시 개선된다.
2. **PR ②** — 대표 지정 API + 앱 카드 star UI.
3. **PR ③** — 파생 7필드 PATCH 거부(D7) + 상세 구매조건 read-only(D2) + 출고 시기 프리셋 4종(D4).
