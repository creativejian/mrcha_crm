# [차선생 CRM → 제프] iM 트림 resolve 회신에 대한 답 — 조사 범위·페이로드·응답 필드 의견

작성 2026-07-27 · 회신 대상: `ref/2026-07-27-jeff-im-capital-trim-resolve-reply.md`
· 최초 문의: `ref/2026-07-27-jeff-im-capital-trim-resolve-request.md`

> **상태**: 부탁 4건 전부 회신 · 조치 A 진행 중(제프) 확인

## 먼저

1건 물었는데 링크 감사까지 돌려서 미신고 오배정 3건·다중 매칭 532건·엔진 미구현 단축까지 열어 주셔서
감사합니다. 특히 **`match_source = "manual"`을 그대로 공개**해 주신 게 저희 입장에서 판단하기 아주 쉬웠습니다.
A(링크 재배정) 먼저 잡아 주신 것도 감사합니다 — 발송 견적이 걸린 건이라 저희도 그 순서가 맞다고 봅니다.

**결론부터: 저희 쪽 조사 범위는 `QT-2607-0012` 1건으로 닫힙니다.** 아래 ①~③ 실측입니다.

---

## ① 11건 표 밖 mc_code로 성공한 iM 견적 — **없습니다**

저희 DB에서 **iM캐피탈로 파트너 계산에 성공한 견적은 `QT-2607-0012` 단 1건**이고, 그게 `MC070526006`입니다.
즉 그쪽 11건 표 안에 있고, ②(b)의 비결정 폴백 경로는 **저희와 무관**합니다.

**`masterMcCode`는 구조적으로 항상 실립니다.** 저희 차량 픽커가 `mcCode`가 없는 트림을
`quotable = false`로 **선택 자체를 막습니다**(그쪽 의미인 "잔가 데이터 보유"를 저희가 그렇게 대응시켰습니다).
그래서 `masterMcCode` 없이 나가는 호출은 만들어질 수 없습니다.

참고로 저희 쪽에 `lender = "iM캐피탈"` 시나리오가 4건 더 있지만 **전부 수기 입력**이라 그쪽 API를 안 탔습니다.

### 저희가 그쪽에 보낸 mc_code 전량 (파트너 계산 성공 6건)

대조에 쓰시라고 전량 붙입니다. `보낸 가격 ≠ resolved 가격`은 iM 1건뿐입니다.

## ② iM + 할인 / iM + 전기차 보조금 — **없습니다**

그 1건이 `discountAmount = 0`, `evSubsidy = 0`이라 ④의 상수 0 고정에 걸린 견적은 없습니다.

다만 **B 정정 전까지는 저희 쪽에서 iM + 할인 조합을 만들지 않도록** 내부적으로 주의하겠습니다.
(지금은 상담사가 금융사를 자유롭게 고를 수 있어서, 할인 있는 견적에 iM을 고르면 그대로 나갑니다.)
B 완료되면 알려주세요 — 그 제약을 풀겠습니다.

## ③ `QT-2607-0012` 요청 페이로드

A 정정 후 확정 월 납입금 계산에 쓰시라고 저희가 보낸 값 그대로 붙입니다.

```jsonc
{
  "lenderCode": "im-capital",
  "productType": "operating_lease",
  "brand": "BMW",
  "modelName": "5 Series",
  "masterMcCode": "MC070526006",
  "quotedVehiclePrice": 74300000,   // 할인 전(base 74,300,000 + option 0)
  "discountAmount": 0,
  "evSubsidyAmount": 0,
  "ownershipType": "company",
  "leaseTermMonths": 60,
  "annualMileageKm": 20000,
  "depositAmount": 0,
  "upfrontPayment": 0,
  "residualMode": "high"
}
```

딜러명·CM/AG 수수료는 미지정입니다. 그쪽 응답의 `majorInputs`
(`depositAmount 0` / `upfrontPayment 0` / `leaseTermMonths 60` / `ownershipType company`)와 일치합니다 —
**차이는 `vehiclePrice` 하나뿐**입니다(74,300,000 → 69,800,000).

## ④ 응답 필드(D) 의견 — 한 필드만 더 부탁드립니다

제안하신 3필드에 찬성합니다. **다만 B를 하고 나면 이번 사고를 잡던 신호가 죽습니다.**

지금 이 사고가 드러나는 이유는 `priceSource: "catalog"`이기 때문인데, B에서 iM이 `quotedVehiclePrice`를
읽도록 고치면 **가격은 항상 저희 값으로 덮이므로** 링크가 엉뚱한 offering을 가리켜도 가격에 흔적이
남지 않습니다. `matchedBy`도 여전히 `master_mc_code`(=exact)일 거고요. **B 이후엔 같은 사고가 조용해집니다.**

그래서 **매칭된 offering의 카탈로그 가격**을 항상 함께 실어 주시면 좋겠습니다:

```jsonc
"resolvedVehicle": {
  "modelName": "The New 5 Series 520i M Sport Package (P1) #116604-1054542",
  "matchedBy": "master_mc_code",   // master_mc_code | model_name | vehicle_key
  "requestedPrice": 74300000,      // 저희가 보낸 quotedVehiclePrice 에코
  "catalogPrice":   74300000,      // ← 추가 요청: 매칭된 offering 자체의 가격
  "vehiclePrice":   74300000,      // 실제 계산에 쓴 값
  "priceSource": "request"         // request | catalog
}
```

`requestedPrice ≠ catalogPrice` → **링크 오배정**. 이게 B 이후에도 살아남는 유일한 축입니다.
이번 건이면 `requested 74,300,000` vs `catalog 69,800,000`으로 **B와 무관하게** 잡혔을 겁니다.

나머지는 그대로 좋습니다:
- `matchedBy: "vehicle_key"` → 저희는 **비결정 경로로 보고 견적을 거부**하겠습니다(⑦ 다중 매칭도 같은 성격).
- `requestedPrice` 에코 → 로그 대조에 유용합니다.

## ⑤ 저희 쪽 조치

1. **응답 가드 — 그쪽 배포를 기다리지 않고 지금 붙입니다.** `resolvedVehicle.vehiclePrice`는 **이미 지금
   응답에 있으므로**, 저희가 보낸 `quotedVehiclePrice`와 대조해 어긋나면 상담사에게 경고하도록 하겠습니다.
   D가 배포되면 `catalogPrice`·`matchedBy` 축으로 확장하겠습니다.
2. **`QT-2607-0012` 재발송** — A 정정 + 확정 월 납입금 받는 대로 진행합니다.
3. 저희 쪽 별건 픽스 하나 공유: 잔존이 `max`일 때 고객 카드에 그쪽 응답의 금액·율 대신 "최대"라는
   문구만 나가던 버그를 오늘 고쳤습니다. 이제 `41,880,000원 (60%)` 형태로 그쪽 값을 **그대로** 표시합니다.
   → **즉 그쪽 응답이 어긋나면 그대로 고객에게 갑니다.** ①의 대조표를 저희가 상시로 보는 이유입니다.

## ⑥ 나머지 항목 — 저희 견적에 걸리는 건 없습니다

| 그쪽 항목 | 저희 상태 |
|---|---|
| ③ iM `MC070126002`(120 M Spt) 오배정 | 해당 견적 **없음** |
| ③ 산은 `MC072526001`(i5) · `MC072726001`(iX1) 오배정 | 해당 견적 **없음** |
| ⑦ 다중 매칭 532건 (BNK 405 · 메리츠 107 · MG 11 · 우리 9) | BNK·메리츠·MG는 **아직 쓴 적 없음**. **우리카드 9건만 잠재 위험** |

**부탁**: ⑦의 **우리카드 9건 mc_code 목록**을 주시면 저희 견적과 대조하겠습니다.
저희가 우리카드로 계산한 건 2건인데 **둘 다 `MC070626003` 한 트림**이라, 그 코드가 9건 목록에
있는지만 알려주셔도 충분합니다.

메리츠 `MC070526006`이 **520d(디젤)와 양쪽에 링크**돼 있다는 건은 저희가 아직 메리츠를 안 써서 사고는
없었지만, 같은 코드라 언제든 저희에게 올 수 있는 건으로 보고 있습니다. C 조치에 포함해 주셔서 감사합니다.

## ⑦ 커버리지에 대해 — 실사용 데이터 하나

⑥에서 "iM 견적이 잘 안 나온다고 느끼셨다면 이 커버리지가 이유"라고 하셨는데, 실제 저희 사용 분포입니다:

| 금융사 | 파트너 계산 성공 건수 |
|---|---|
| 우리카드 | 2 |
| 산은캐피탈 | 2 |
| 신한카드 | 1 |
| iM캐피탈 | **1** |

저희가 아직 도입 초기라 표본이 작아서 커버리지 체감을 말씀드리긴 이릅니다. 다만 **iM 링크 11건 중
2건이 틀린 상태에서 저희가 쓴 1건이 그 2건 중 하나였다**는 건, 표본이 커지기 전에 잡힌 게 다행이라고 봅니다.

농협(0%)·MG 렌트(0%)는 저희 금융사 목록에는 있지만 아직 견적을 만든 적이 없습니다.
